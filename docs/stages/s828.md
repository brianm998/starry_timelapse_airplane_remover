# s828: client catalogue parity check

Summary: `i18n/client_parity.py` fails CI when a catalogue key is referenced by only one of the gui and the desktop client unless `i18n/client-parity-allowlist.json` gives a reason.

The scan finds 84 one-sided keys today, all StarCore text; the 2026-11-21 estimate of ~170 `ui.*` keys is stale, since the ui keys are balanced. Engine-rendered keys (`warning.*`, `severity.*`, `run_marker.*`) reach the desktop already localised through stard and are allowlisted as `engine`. `operation.*` and `progress.frames_in_*` are real gaps (the desktop progress dialog lacks them), filed as two MASON proposals. Wired into the pr-gate static job (the `t0-i18n` suite line in `.mason/mason.toml` is left to its own task); tests in `i18n/tests/test_client_parity.py`. No catalogue keys change.

No exit script: any file under `scripts/` routes the change into `test-pipeline`, whose narrowed run currently fails with no tests when no pipeline test is reached. To verify by hand: `python3 i18n/client_parity.py && python3 i18n/tests/test_client_parity.py && python3 i18n/check.py`.
