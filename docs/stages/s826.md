# s826: binary keypoint files

Summary: keypoint files are written as compact binary `.kpb` (magic `STARKP01`) instead of YAML, ~4.7x smaller and ~370x faster to load, while existing `.yaml` files still load and are not re-detected.

`ocv_feature_set_write` writes binary for a `.kpb` name; `ocv_feature_set_load` detects the magic and falls back to `cv::FileStorage`. `Config.existingKeypointPath` tries `.kpb` then `.yaml`; the on-disk survey and `KeypointOp.hasWorkToDo` count either form; stale-keypoint invalidation deletes both. Measured on a synthetic 4240x2832 sky (no real frame on hand): YAML 1,562,040 bytes / 64.4 ms, `.kpb` 332,144 bytes / 0.17 ms (min of 15, release).

`test-StarCpp-qos` needs 3 tests to run, and on this Intel Mac one of its 3 skips, so any StarCpp change was red. `OpenCVQoSTests` gains `testWorkersInheritAUserInitiatedCaller`, which runs everywhere and checks that a raised caller's OpenCV workers are neither lowered nor raised past its class. The `.mason/` floor edit from an earlier round was reverted: the base's definition is what runs.

No exit script: verify with `swift test --package-path StarCpp --filter 'OCVFeatureSetBinaryTests|OpenCVQoSTests'` and `swift test --package-path StarCore --filter 'KeypointFileCompatibilityTests|ArtifactInvalidationTests'` (with `STAR_USE_GPU_FOR_MERGE=0`).
